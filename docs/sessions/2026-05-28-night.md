## Архитектура «Anti-shutdown VPN»

```
📱 Мобильный (МТС/Билайн/Мегафон)
  ↓ ClientHello SNI=api-maps.yandex.ru на 443
  ↓ DPI: whitelist → пропускает
  ↓
🇷🇺 Yandex Cloud VM ru-relay-1
  ├─ Xray Reality (in), dest=api-maps.yandex.ru:443
  ├─ Smart routing:
  │   • geoip:ru → direct (РФ IP, Сбер/Госуслуги работают)
  │   • else → outbound aeza-relay (chain к Frankfurt)
  └─ Outbound "aeza-relay" → VLESS-туннель к Aeza Frankfurt
🇩🇪 Aeza Frankfurt (текущий зарубежный exit)
  └─ выход с DE IP (YouTube/Insta работают)
```

**Ключевой инсайт:** для shutdown-bypass нужен **РФ-located** сервер
(потому что cert chain должен matches whitelist-домен, а только из РФ
yandex.ru резолвится в РФ Yandex IP). С зарубежного сервера whitelist-SNI
не сработает.

**Конкуренты:** StealthSurf делает то же — 16 РФ-VPS на инфраструктуре
Beeline B2O CDN, Yandex Cloud, Cloud.ru. Используют SNI типа
`gp.x5.ru`, `api-maps.yandex.ru`, `iv.kommersant.ru`, `www.vk.com`,
`cdp.x5.ru`. Подробности в Obsidian → `[[Claude session log]]`.

## Важные warning'и для Claude'a Олега

1. **НЕ менять SNI/dest на проде вслепую.** Обязательно сверять что
   cert chain matches:
   ```bash
   openssl s_client -connect <dest>:443 -servername <new_sni> </dev/null 2>&1 | grep -E "subject|verify"
   ```
2. **«VPN не работает в РФ» = смотреть на ПОРТ в первую очередь.** Не
   SNI, не shutdown-whitelist. 95% случаев — порт.
3. **404 от агента (`list_peers(vless): 404`) КРИТИЧНО.** В прошлый раз
   я (Sonnet) пропустил → был money leak: counters не считались →
   юзеры качали unlimited. Зафиксил Opus 28.05.
4. **Не делать SSH-ключевой setup для рф-relay без согласования.**
   Yandex Cloud по умолчанию включает OS Login — нужно либо через него,
   либо отключить и поставить обычные ключи. Этот вопрос ещё открыт.

## ⛔ UPDATE 29.05 — ru-relay IP СОЖЖЁН на МТС-мобильном (Opus 4.8 + Олег)

> POC выше работал **только** с Mac через SOCKS5 (Егор) и с домашнего
> WiFi. Реальный тест с **МТС-мобильного Олега (Ижевск)** — провал.

**Что сделали:** временно подняли простую HTTP тест-страницу на
`93.77.188.143:443` (вместо xray), чтобы изолировать вопрос «долетает ли
TCP с мобильного вообще» — без Reality/Happ/chain.

**Результат (железобетонный):**
- Тест-страница отвечает **HTTP 200** на: bot-VPS (Германия), DO Amsterdam,
  локальную машину — т.е. достижима из всего интернета.
- С **МТС-сети Олега — НОЛЬ SYN-пакетов** (tcpdump), Safari «не удалось
  подключиться к серверу». Даже под сторонним VPN не открывается (VPN
  split-route'ит `.ru`-IP мимо туннеля → прямой путь → тот же блок).

**Вывод:** `93.77.188.143` заблокирован **на IP-уровне самим МТС**. Не код,
не Reality, не конфиг. Причём блок появился ПОСЛЕ вчерашних многочасовых
Reality-хендшейков → гипотеза: **МТС DPI зафингерпринтил IP как VPN-сервер
и закатал в блок-лист** (вчера WiFi пускал, сегодня уже нет).

**Опровергнутая гипотеза:** «Yandex Cloud customer-IP (AS200350) в
operator-whitelist». Для МТС-Ижевск — НЕТ. Yandex Cloud customer-VPS режется
как обычный VPN-хостинг (DO/Aeza).

**Системный урок:** статичный РФ-IP + Reality = МТС банит IP за часы. Для
anti-shutdown нужна **ротация IP** ИЛИ **operator-internal инфра (Beeline
B2O CDN)** ИЛИ **CDN-фронтинг** — то, что StealthSurf делает 16-ю серверами.
Это инфраструктурная R&D-задача, НЕ выходной проект.

**Решение:** anti-shutdown — **на паузу**. Не блокер запуска. Фокус на
обычном продукте (VLESS 443 + триал + платежи — готовы). ru-relay-1 оставлен
с chain-конфигом (работает для не-МТС-путей), но как продукт для МТС не годен.

**Если возвращаться:** сначала тест с Билайн/Мегафон SIM (может только МТС
так жёсток) + Cloud.ru/VK Cloud VPS (StealthSurf использует их, не Yandex
Cloud) — ДО любой инфраструктурной стройки.

## ⛔ UPDATE 31.05 — vk.com SNI тоже не помог, IP-level бан подтверждён (Sonnet 4.6 + Егор)

> Тест из Удмуртии (реальный shutdown-режим МТС) с **новым IP `158.160.43.171`**
> (Yandex перевыдал после смены публичного IP).

**Что сделали и что увидели:**

1. **Новый IP `158.160.43.171` сначала работал** (10:21–10:27 UTC): tcpdump поймал
   6 SYN с мобильного, Reality-туннель поднялся, access.log показал 277 accepted-строк,
   Instagram реально лился через Франкфурт (`aeza-fra`). IP в whitelist, SYN проходил.

2. **Через ~1.5ч активности** — и Instagram, и YouTube перестали грузить через туннель.
   Трафик к серверу упал 277→62 строки, потом до нуля. Цепочка на Франкфурт жива (43мс,
   15 МБ/с), Frankfurt→YouTube 200 OK — проблема только в первом хопе телефон→ru-relay.

3. **Мигрировали SNI с `api-maps.yandex.ru` → `vk.com`** (cert `*.vk.com`, GlobalSign,
   TLS 1.3 + h2, verify 0 — всё по правилам). Запустили testpage на 443.

4. **testpage не получила ни одного хита с мобильного** (tcpdump = 0 за 60 сек).
   С Mac — HTTP 200 мгновенно. Значит МТС заблокировал `158.160.43.171` на IP-уровне,
   SNI вообще не имеет значения — до TLS-хендшейка пакеты не доходят.

**Финальный вывод (подтверждает Олегов 081ce22):**

МТС-DPI в shutdown-режиме **банит Yandex Cloud customer-VPS по IP-паттерну** за
~1.5-2 часа реальных Reality-хендшейков. Смена SNI не помогает — блок IP-level.
Оба IP (93.77.x и 158.160.x) сгорели по одному паттерну.

**Anti-shutdown — официально на паузу.** Требует:
- IP-ротации (обновлять каждые N часов) — нужна автоматизация
- ИЛИ VK Cloud/Cloud.ru VPS (StealthSurf их использует, не Yandex Cloud)
- ИЛИ CDN-фронтинг (Beeline B2O / CDNetworks — как StealthSurf)

Это инфраструктурная R&D, не выходной проект. Не блокер запуска.

**Если тестировать снова:** сначала Билайн/Мегафон SIM (может МТС жёстче других),
потом VK Cloud VPS (vk.com AS47764 — вероятно в whitelist как operator-internal).
